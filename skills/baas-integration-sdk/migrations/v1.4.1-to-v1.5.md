# v1.4.1 → v1.5.0 마이그레이션

**앱 조치 없음(Tier 0)** — SDK 표면은 한 글자도 바뀌지 않았고(`sdk/` 미변경, CDN 채널 무영향),
서버의 `settings.access` 기능도 그대로다. 바뀐 것은 **이 스킬이 무엇을 설계하게 하느냐** 하나다.
이미 만들어진 앱은 자기 정책 그대로 동작한다.

## 무엇이 빠졌나

컬렉션 **접근 정책을 설계하는 어휘**를 이 스킬에서 제거했다.

- `settings.access = {create, read, update, delete}` 와 atom 목록(`public|member|owner|ref_owner:<field>`)
- "기본값과 달라지는 연산만 명시한다" 는 설계 지침
- `ref_owner` 기반 자식 컬렉션 access 패턴과 union read 소비 규약

남은 것은 **플랫폼 기본값 하나**다 — 로그인한 회원이 컬렉션 전체를 조회하고, 각 행은 만든 사람만
수정·삭제한다. 이 스킬을 읽는 구현자는 그 기본 위에서 UI 를 만들고, 연산별 권한을 정하지 않는다.

## 왜 뺐나

**베껴 넣은 정책은 그 순간 굳는다.** 네이티브 기능을 확장하는 컬렉션(게시판 글에 딸린 잔여 필드
등)은 부모 리소스의 설정을 보고 access 를 정하게 되는데, 부모는 운영자가 콘솔에서 바꾼다.
바뀌는 순간 베낀 값은 낡고, 아무도 알아채지 못한다. 두 저장소·두 어휘 사이에 잇는 참조가 없어서
동기화될 방법 자체가 없다.

어휘를 주면 사람이 값을 정하고, 값을 정하면 굳는다. 그래서 **어휘를 없애는 쪽**이 맞다.

## 기본과 다른 게 필요하면 — 규칙이다

호출자를 구분해야 하거나(누구는 되고 누구는 안 됨), 조회 범위를 좁혀야 하거나(내 것만·승인된
것만), 비로그인이 읽어야 하거나, 접근이 다른 리소스를 따라가야 하면 그건 전부 **규칙**이고
`baas-backend`(`serverFn`)가 판정한다. `serverFn` 은 현재 값을 그때그때 읽으므로 낡지 않는다.

특히 **클라이언트 필터는 조회 범위 축소가 아니다.** 행이 이미 브라우저에 도착한 뒤 돌기 때문에
표시 편의일 뿐 보호가 아니다.

## 기존 앱에 명시 정책이 있으면

**손대지 않아도 된다.** 서버는 여전히 `settings.access` 를 강제하고, 이미 선언된 정책은 그대로
동작한다. 이 변경은 앞으로의 설계 지침이지 마이그레이션 지시가 아니다.

다만 그 앱에서 접근을 **바꿔야 할 요구**가 올라오면, 그때는 정책을 고치는 대신 규칙으로 올린다 —
같은 이유로 다시 굳기 때문이다.
