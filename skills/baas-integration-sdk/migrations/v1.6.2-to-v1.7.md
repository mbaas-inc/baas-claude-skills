# v1.6.2 → v1.7.0 마이그레이션

**커스텀 원장에 결제를 붙일 수 있다.** 지금까지 결제는 네이티브 스토어 · 예약에만 있어, 예약을 커스텀
백엔드(컬렉션 원장)로 만든 앱은 예약금 결제를 — 테스트 결제조차 — 붙일 수 없었다(미용실 예약 E2E,
2026-10-06). 이제 커스텀 백엔드(serverFn)가 금액을 정해 결제 세션을 만들고 승인하며, 앱은 위젯만 띄운다
(aiapp-service#900).

## 무엇이 바뀌었나

| 위치 | 전 | 후 |
|---|---|---|
| `usePayment()` | `fetchTerms` | `beginWidget(session, 셀렉터)` · `getRedirectResult()` 추가 |
| core | `getPurchaseTerms` | `beginPaymentWidget` · `getPaymentRedirectResult` 추가 |
| 서버 SDK(`baas-backend`) | — | `sdk.payments.create · get · confirm · cancel` |
| `reference/sdk-surface.md` 「커스텀 화면에 결제를 붙일 때」 | store · reservation 경유만 | serverFn 세션 → 위젯 → 복귀 → serverFn 승인 흐름 |

- 세션 응답의 `payment_mode` 가 `test` 면 테스트 결제다(실제 청구 없음). 판매자 승인 전 프로젝트는 모두 test 다
  (aiapp-service#898). 화면에 「테스트 결제」 안내를 띄운다.

## 무엇이 바뀌지 않았나

- 스토어 · 예약 결제(`beginWidgetCheckout`)와 위젯 규칙(동기 `requestPayment`, `USER_CANCEL` 무시, 구매약관
  동의, 통신판매중개 고지)은 그대로다.
- 금액 · 결제 상태를 커스텀 필드에 두고 클라이언트가 쓰는 것은 여전히 금지다 — 상태의 정본은 서버(`payments.get`)다.

## 적용 절차

- **앱**: 조치할 것이 없다. 커스텀 원장에 결제를 붙일 때만 위 흐름을 쓴다.
- 예전 안내대로 「결제는 스토어 · 예약을 경유」하려고 원장과 네이티브 예약을 이중으로 두었다면, 커스텀 결제로 바꿀 수 있다.
