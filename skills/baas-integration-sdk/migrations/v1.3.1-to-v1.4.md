# v1.3.1 → v1.4.0 마이그레이션

**앱 조치 없음(Tier 0)** — 기존 호출·반환 타입·화면 규약이 하나도 바뀌지 않았다. 전부 **추가**다.
동적 컬렉션을 쓰지 않는 앱은 완전히 무영향이고, 쓰는 앱도 재생성 대상이 아니다.

동적 컬렉션이 실사용 가능한 수준으로 올라오면서(aiapp-service #703) 그 표면을 SDK 에 붙였다.
지금까지 "SDK 로는 안 되니 클라이언트에서 순회해 계산" 하던 것들이 서버 연산으로 대체된다.

## 무엇이 추가됐나

### `useCollection()` 반환값

```diff
  const { records, record, loading, error,
          fetchRecords, fetchPublicRecords, fetchRecord,
          submitRecord, editRecord, removeRecord,
+         fields,                                    // includeFields 로 받은 렌더 스키마
+         restore, increment, aggregate, batch, transaction,
        } = BaasSDK.useCollection();
```

### 기존 함수의 선택 인자

| 함수 | 추가된 것 |
|---|---|
| `fetchRecords(name, opts)` | `opts.or`(OR 조건) · `opts.includeFields` |
| `fetchRecord(name, id, opts)` | `opts.includeFields` |
| `submitRecord(name, data, opts)` | `opts.clientTxnId`(멱등 생성) |

`fetchRecord` 의 3번째 인자는 원래 **무시되던 `_isPublic`** 이었다(경로 통합 후 의미가 없어졌다).
객체로 바뀌었지만 `fetchRecord(name, id, true)` 를 넘겨도 `includeFields` 가 falsy 로 읽혀
**동작이 같다** — 그래서 Tier 0 이다.

### core 함수 (훅 없이 쓰는 경우)

`aggregateRecords` · `incrementRecord` · `restoreRecord` · `batchRecords` · `runTransaction`

### 필드 타입

`array` 추가(태그·다중 선택). `options.values` 가 있으면 그 목록에서만 고른다.
필터 연산자는 `has`(요소 포함) 하나뿐이다 — 등호는 배열 전체 일치인지 요소 포함인지 모호하고
범위 비교는 정의가 없어서, 조용히 이상한 결과를 주는 대신 거부한다.

## 어떤 우회를 걷어낼 수 있나

기존 앱에 아래 패턴이 있으면 교체할 수 있다. **강제는 아니다**(기존 코드도 계속 동작한다).

| 지금까지 하던 우회 | 대체 |
|---|---|
| 페이지를 순회해 클라이언트에서 합산 | `aggregate(name, "sum", { field })` |
| 조건별로 두 번 조회해 합집합 | `fetchRecords(name, { or: {...} })` |
| 단건 생성을 반복 호출 | `batch(name, { create: [...] })` |
| 조회수를 읽어서 +1 해 저장 | `increment(name, id, "views")` |
| 삭제 확인 UX 를 강하게 (복구 불가라) | `restore(name, id)` |
| 폼 재시도 시 중복 접수를 서버에서 못 막음 | `submitRecord(..., { clientTxnId })` |
| 필드 목록을 앱에 하드코딩 | `includeFields: true` → `fields[i].widget` |

특히 **읽어서 +1 해 저장하는 조회수**는 동시 요청이 서로의 증가를 덮어 값이 새고 있었을 수 있다.
`increment` 는 서버가 DB 안에서 더하므로 유실되지 않는다.

## 렌더 스키마 — `widget` 하나만 본다

`includeFields: true` 로 받으면 필드마다 `widget` 이 온다. **서버가 확정한 결론**이므로
`type`·`ui` 를 보고 폴백을 계산하지 않는다.

```tsx
await fetchRecords("notice", { includeFields: true });

fields?.map((f) => {
  switch (f.widget) {
    case "richtext": return <Editor label={f.label ?? f.name} required={f.required} />;
    case "toggle":   return <Switch label={f.label ?? f.name} />;
    case "select":   return <Select options={f.options?.values} />;
    case "radio":    return <Radio  options={f.options?.values} />;
    case "tags":     return <TagInput />;
    // text · textarea · phone · email · number · money · date · reference
  }
});
```

폴백 규칙을 앱에서 다시 구현하면 규칙이 갈라진다 — 예를 들어 `enum` 은 값이 3개 이하면 `radio`,
넘으면 `select` 인데 그 경계를 앱이 따로 들고 있으면 서버가 기준을 바꿀 때 화면만 어긋난다.

## 주의할 것

- **배치와 트랜잭션은 반대 도구다.** 배치는 같은 컬렉션 대량 + **부분 성공**(실패한 행만 건너뛴다),
  트랜잭션은 복수 컬렉션 소수 + **전부 아니면 전무**. 대량 작업에 트랜잭션을 쓰면 한 행 때문에
  전부 되돌아간다.
- **배치의 실패 사유를 버리지 말 것.** `results[i].error` 를 행별 오류 표시에 그대로 쓴다 —
  "3건 실패" 만 보여주면 사용자가 무엇을 고쳐야 할지 모른다.
- **멱등 키는 제출 1회당 하나를 만들어 재시도 사이에 유지한다.** 매번 새로 만들면 의미가 없다.
- **`unique` 필드 중복은 409** 다. 해당 입력에 "이미 사용 중" 을 붙인다.
- **삭제가 409 로 막힐 수 있다** — 참조하는 데이터가 있는 경우(`on_delete: restrict`, 기본값).
  오류 메시지에 막는 컬렉션·건수가 담기므로 그대로 노출해도 된다.
- **"누구나 조회수만 올리기" 는 아직 안 된다.** `increment` 는 `update` 권한을 쓰므로 비로그인
  증가에는 `update: public` 이 필요하고 그건 본문 수정까지 열어 버린다. 필드 단위 권한이 없어서
  생기는 제약이고, 로그인 회원 기준 카운터나 관리자 경로에서는 문제없다.
- **성능**: 등호·`has` 만 인덱스를 탄다. `like`·범위 비교·커스텀 필드 정렬은 전체 스캔이다.
  큰 컬렉션에서 목록·집계 UX 를 설계할 때 필터로 먼저 좁힌다. `limit` 상한은 100.

## 아직 없는 것

커서 페이징 · `image`/`file` 위젯(스토리지 URL 을 string 필드에 저장) · 필드 단위 권한 ·
복합 유니크(여러 필드 조합) · 다중 정렬.
