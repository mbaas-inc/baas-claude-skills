# v0.10 → v0.10.4 마이그레이션 (패치 묶음)

**결제 confirm 필드를 `order_no` 로 통일하는 과정.** 백엔드 계약이 두 번 바뀌면서 SDK 가 따라간 패치 4건이라, 결과만 보면 **앱 조치가 없다**(Tier 0).

> 이 노트는 사후 작성됐다. 0.10.1~0.10.4 각각에 문서를 남기지 않아 구간이 비어 있었고, 이력 보존을 위해 묶어서 채웠다.

## 최종 상태 (0.10.4)

| 도메인 | confirm 필드 |
|---|---|
| store | **`order_no`** |
| reservation | **`order_no`** |

토스가 주는 `orderId`(camelCase)는 그대로 두고, 백엔드로 보낼 때 `order_no` 로 보낸다.

## 왜 4번에 걸쳐 바뀌었나

| 버전 | 변경 | 계기 |
|---|---|---|
| 0.10.1 | store confirm: `order_no` → `order_id`, `terms_agreed` 추가 | 백엔드가 `order_id`+`terms_agreed` 를 요구했다 |
| 0.10.2 | store confirm: 앱 입력 `order_id` → 백엔드 `order_no` 로 **번역** | 백엔드 PR #640 이 필드를 `order_no` 로 바꿨다 |
| 0.10.3 | 번역 제거 — 앱·SDK·백엔드 모두 **`order_no`** 로 통일 | 번역 계층이 혼란을 키웠다 |
| 0.10.4 | reservation 도 `order_no` 로 통일 | store 와 필드가 달라 헷갈렸다 |

0.10.2 의 "필드 번역"은 SDK 가 transport 계층으로서 앱을 보호한 사례다 — **CDN 갱신만으로 앱 재빌드 없이 백엔드 변경을 흡수**했다. 다만 앱과 백엔드가 서로 다른 이름을 쓰는 상태가 남아 0.10.3 에서 정리했다.

## 앱 조치

**없다.** 0.10.0 에서 0.10.4 로 바로 올라오면 `confirmOrder` 호출부에 변화가 없다(중간 단계에서만 필드가 흔들렸다).

0.10.1~0.10.3 중간 버전에 핀돼 있었다면 `order_no` 기준으로 맞추면 된다.

## 함께 들어온 것 (0.10.3)

- **결제 버튼 라벨 규약** — "결제하기"(또는 "N원 결제하기"). 위젯이 카드·계좌이체·간편결제를 모두 제공하므로 **"카드로 결제하기" 같은 수단 한정 문구 금지**.
- 문서·주석 전반의 "카드결제" 프레이밍을 "결제(위젯)"로 정리.
